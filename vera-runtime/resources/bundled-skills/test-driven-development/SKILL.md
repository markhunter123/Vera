# 测试驱动开发 (TDD)

## 概述

先写测试。看着它失败。写最小量的代码让它通过。

**核心原则：** 如果你没有亲眼看到测试失败，你就不知道它是否测试了正确的东西。

**违反规则的文字就是违反规则的精神。**

## 何时使用

**始终使用：**
- 新功能
- Bug 修复
- 重构
- 行为变更

**例外（先问用户）：**
- 一次性原型
- 自动生成的代码
- 配置文件

想着"就这一次跳过 TDD"？打住。那是在找借口。

## 铁律

```
没有先写失败的测试，就不许写生产代码
```

先写代码再写测试？删掉代码。从头开始。

**没有例外：**
- 不要留着当"参考"
- 不要在写测试时"改编"它
- 不要看它
- 删掉就是删掉

从测试出发，全新实现。就这样。

## 红-绿-重构循环

### 红色 — 写一个失败的测试

写一个最小的测试，展示应该发生什么。

**好的测试：**
```python
def test_retries_failed_operations_3_times():
    attempts = 0
    def operation():
        nonlocal attempts
        attempts += 1
        if attempts < 3:
            raise Exception('fail')
        return 'success'

    result = retry_operation(operation)

    assert result == 'success'
    assert attempts == 3
```
命名清晰，测试真实行为，只测一件事。

**坏的测试：**
```python
def test_retry_works():
    mock = MagicMock()
    mock.side_effect = [Exception(), Exception(), 'success']
    result = retry_operation(mock)
    assert result == 'success'  # 重试次数呢？时序呢？
```
命名模糊，测试的是 mock 而不是真实代码。

**要求：**
- 每个测试只测一个行为
- 命名清晰有描述性（名字里有"和"？拆成两个测试）
- 用真实代码，不用 mock（除非真的无法避免）
- 名称描述的是行为，而不是实现

### 验证红色 — 看着它失败

**强制步骤，绝不可跳过。**

```bash
# 使用终端工具运行具体测试
pytest tests/test_feature.py::test_specific_behavior -v
```

确认：
- 测试失败（不是因为拼写错误导致的报错）
- 失败信息符合预期
- 因为功能缺失而失败

**测试直接通过了？** 你测试的是已有行为。修正测试。

**测试报错了？** 修掉报错，重新跑直到它正确地失败。

### 绿色 — 最小量代码

写最简单的代码让测试通过。绝不多写。

**好的：**
```python
def add(a, b):
    return a + b  # 没有多余的东西
```

**坏的：**
```python
def add(a, b):
    result = a + b
    logging.info(f"Adding {a} + {b} = {result}")  # 多余的！
    return result
```

不要加功能、重构其他代码，或超出测试范围地"改进"。

**绿色阶段可以作弊：**
- 硬编码返回值
- 复制粘贴
- 重复代码
- 跳过边界情况

我们会在重构阶段修好。

### 验证绿色 — 看着它通过

**强制步骤。**

```bash
# 运行具体测试
pytest tests/test_feature.py::test_specific_behavior -v

# 然后运行全部测试，检查是否有回归
pytest tests/ -q
```

确认：
- 测试通过
- 其他测试仍然通过
- 输出干净（无错误、无警告）

**测试失败？** 修代码，不要修测试。

**其他测试失败？** 立即修复回归。

### 重构 — 清理

只有在绿色之后才能：
- 消除重复
- 改进命名
- 提取辅助函数
- 简化表达式

全程保持测试绿色。不要添加行为。

**重构期间测试失败：** 立即撤销，步子再小一点。

### 重复

下一轮为下一个行为写失败的测试。一次一个循环。

## 为什么顺序很重要

**"我写完再补测试来验证正确性"**

代码写完之后写的测试会立刻通过。立刻通过说明不了任何问题：
- 可能测的是错误的东西
- 可能测的是实现而非行为
- 可能漏掉了你忘记的边界情况
- 你从没见过它捕获 bug

测试先行迫使你亲眼看到测试失败，证明它确实在测某种东西。

**"我已经手动测了所有边界情况"**

手动测试是随意的。你以为自己全都测了，但是：
- 没有你测过什么的记录
- 代码变更后无法重新运行
- 压力下容易忘记某些情况
- "我试的时候没问题" ≠ 全面覆盖

自动化测试是系统性的。每次运行方式都完全一样。

**"删掉 X 小时的工作是在浪费时间"**

沉没成本谬误。时间已经花出去了。你现在的选择是：
- 删掉用 TDD 重写（高信心）
- 保留代码事后补测试（低信心，大概率有 bug）

真正的"浪费"是保留你无法信任的代码。

**"TDD 太教条了，务实意味着灵活变通"**

TDD 就是务实：
- 在提交前发现 bug（比事后调试更快）
- 防止回归（测试立刻捕获破坏性变更）
- 文档化行为（测试展示如何使用代码）
- 使重构成为可能（随意改，测试来兜底）

"务实"的捷径 = 生产环境调试 = 更慢。

**"事后测试达到同样目的——这是精神而非仪式"**

不是。事后测试回答的是"它做了什么？"。测试先行回答的是"它应该做什么？"

事后测试被你的实现带偏了。你测试的是你构建的东西，而不是需求。测试先行迫使你在实现之前就发现边界情况。

## 常见借口

| 借口 | 现实 |
|--------|---------|
| "太简单了不值得测" | 简单的代码也会出错。写个测试就 30 秒。 |
| "我之后再测" | 测试立刻通过什么也证明不了。 |
| "事后测试达到同样目的" | 事后测试 = "它做了什么？" 测试先行 = "它应该做什么？" |
| "已经手动测过了" | 随意 ≠ 系统。没有记录，无法重跑。 |
| "删掉 X 小时是浪费" | 沉没成本谬误。保留未验证的代码是技术债。 |
| "留着当参考，先写测试" | 你会改编它。那就是事后测试。删掉就是删掉。 |
| "需要先探索" | 没问题。扔掉探索代码，用 TDD 开始。 |
| "难测 = 设计不清晰" | 听测试的话。难测 = 难用。 |
| "TDD 会拖慢我" | TDD 比调试快。务实 = 测试先行。 |
| "手动测试更快" | 手动证明不了边界情况。每次改动你都得重测。 |
| "现有代码没有测试" | 你在改进它。为你碰到的代码加测试。 |

## 红色警报 — 停下来重新开始

如果你发现自己正在做以下任何一件事，删掉代码，用 TDD 重来：

- 先写代码再写测试
- 实现之后再测
- 测试第一次运行就通过
- 解释不了测试为什么失败
- 测试是"之后再加"的
- 在合理化"就这一次"
- "我已经手动测过了"
- "事后测试能达到同样目的"
- "留着当参考"或"改编现有代码"
- "已经花了 X 小时，删掉太浪费"
- "TDD 太教条，我是务实的"
- "这次不一样因为……"

**以上所有都意味着：删掉代码，用 TDD 重新开始。**

## 验证清单

标记工作完成之前：

- [ ] 每个新函数/方法都有测试
- [ ] 实现之前亲眼看到每个测试都失败过
- [ ] 每个测试都因预期的原因失败（功能缺失，而非拼写错误）
- [ ] 只写了最小量的代码让每个测试通过
- [ ] 全部测试通过
- [ ] 输出干净（无错误、无警告）
- [ ] 测试使用真实代码（只有在无法避免时才用 mock）
- [ ] 边界情况和错误都已覆盖

不能全部打勾？你跳过了 TDD。重新开始。

## 卡住时

| 问题 | 解决方案 |
|----------|----------|
| 不知道怎么测 | 写出你期望的 API。先写断言。问用户。 |
| 测试太复杂 | 设计太复杂。简化接口。 |
| 全部都得 mock | 代码耦合太高。用依赖注入。 |
| 测试准备代码太多 | 提取辅助函数。还是复杂？简化设计。 |

## Agent 集成

### 运行测试

每个步骤使用 `terminal` 工具运行测试：

```python
# 红色 — 验证失败
terminal("pytest tests/test_feature.py::test_name -v")

# 绿色 — 验证通过
terminal("pytest tests/test_feature.py::test_name -v")

# 全套 — 验证无回归
terminal("pytest tests/ -q")
```

### 与 delegate_task 配合

派发子 Agent 实现功能时，在 goal 中强制执行 TDD：

```python
delegate_task(
    goal="使用严格 TDD 实现 [功能]",
    context="""
    遵循 test-driven-development 技能：
    1. 先写失败的测试
    2. 运行测试验证它失败
    3. 写最小量代码让它通过
    4. 运行测试验证它通过
    5. 需要时重构
    6. 提交

    项目测试命令：pytest tests/ -q
    项目结构：[描述相关文件]
    """,
    toolsets=['terminal', 'file']
)
```

### 与 systematic-debugging 配合

发现 bug？写一个复现它的失败测试。遵循 TDD 循环。测试既证明修复有效，又防止回归。

绝不写没有测试的 bug 修复。

## 测试反模式

- **测试 mock 行为而非真实行为** — mock 应该验证交互，而非代替被测系统
- **测试实现细节** — 测试行为/结果，而非内部方法调用
- **只测 happy path** — 始终测试边界情况、错误和临界值
- **脆弱的测试** — 测试应该验证行为而非结构；重构不应破坏测试

## 终极法则

```
生产代码 → 测试已存在且先失败过
否则 → 不是 TDD
```

未经用户明确许可，没有例外。
