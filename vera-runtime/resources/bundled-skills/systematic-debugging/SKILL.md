# 系统化调试

## 概述

胡乱修复既浪费时间又制造新 bug。快速补丁只是掩盖了底层问题。

**核心原则：** 永远先找根因，再尝试修复。修复症状就是失败。

**违反本流程的字面规定，就是违反调试精神本身。**

## 铁律

```
不完成根因调查，不得提出任何修复方案
```

没完成阶段 1，就不能提修复方案。

## 适用场景

适用于任何技术问题：
- 测试失败
- 生产环境 bug
- 异常行为
- 性能问题
- 构建失败
- 集成问题

**尤其在以下情况务必使用：**
- 时间紧迫时（紧急情况最容易让人想猜）
- "就快速改一下"看起来很合理时
- 已经试过多次修复时
- 上次修复不管用时
- 还没完全理解问题时

**以下情况不能跳过：**
- 问题看起来很简单（简单问题同样有根因）
- 赶时间（仓促行事必然返工）
- 有人要求立刻修好（系统化比乱撞更快）

## 四个阶段

每个阶段必须完成后才能进入下一阶段。

---

## 阶段 1：根因调查

**在尝试任何修复之前：**

### 1. 仔细阅读报错信息

- 不要跳过错误或警告
- 报错信息里往往就藏着答案
- 完整阅读堆栈跟踪
- 注意行号、文件路径、错误码

**行动：** 对相关源文件使用 `read_file`。用 `search_files` 在代码库中搜索报错字符串。

### 2. 稳定复现

- 能否可靠触发？
- 精确步骤是什么？
- 每次都会发生吗？
- 如果无法复现 → 收集更多数据，不要猜测

**行动：** 使用 `terminal` 工具运行失败的测试或触发 bug：

```bash
# 运行指定的失败测试
pytest tests/test_module.py::test_name -v

# 以详细模式运行
pytest tests/test_module.py -v --tb=long
```

### 3. 检查最近变更

- 什么改动可能导致这个问题？
- Git diff、最近的提交
- 新的依赖、配置变更

**行动：**

```bash
# 最近提交
git log --oneline -10

# 未提交的更改
git diff

# 特定文件的变更历史
git log -p --follow src/problematic_file.py | head -100
```

### 4. 多组件系统：收集证据

**当系统涉及多个组件时（API → 服务 → 数据库、CI → 构建 → 部署）：**

**在提出修复方案之前，先添加诊断埋点：**

对每个组件边界：
- 记录进入该组件的数据
- 记录离开该组件的数据
- 验证环境/配置的传递
- 检查每一层的状态

运行一次收集证据，证明问题出在哪。
然后分析证据，确定出问题的组件。
然后针对该组件深入调查。

### 5. 追踪数据流

**当错误出现在调用栈深处时：**

- 坏数据从哪里来？
- 是谁用坏数据调用了这个函数？
- 一直向上追溯，直到找到源头
- 在源头修复，不要在症状处修复

**行动：** 使用 `search_files` 追踪引用：

```python
# 找到函数在哪里被调用
search_files("function_name(", path="src/", file_glob="*.py")

# 找到变量在哪里被赋值
search_files("variable_name\\s*=", path="src/", file_glob="*.py")
```

### 阶段 1 完成检查清单

- [ ] 完整阅读并理解了报错信息
- [ ] 问题已稳定复现
- [ ] 已识别并审查最近变更
- [ ] 已收集证据（日志、状态、数据流）
- [ ] 问题已定位到具体组件/代码
- [ ] 已形成根因假设

**停：** 在弄清楚为什么会发生之前，不要进入阶段 2。

---

## 阶段 2：模式分析

**修复之前先找模式：**

### 1. 找到正常工作的示例

- 在同一个代码库中定位类似但正常运行的代码
- 有和出问题的代码相似但能正常工作的吗？

**行动：** 用 `search_files` 找到可对比的模式：

```python
search_files("similar_pattern", path="src/", file_glob="*.py")
```

### 2. 对照参考实现

- 如果正在实现某种模式，完整阅读参考实现
- 不要略读——逐行阅读
- 在应用之前完全理解这个模式

### 3. 找出差异

- 正常和出问题之间有什么不同？
- 列出每一个差异，再小也不放过
- 不要假设"那个应该不影响"

### 4. 理清依赖

- 这需要哪些其他组件？
- 需要什么设置、配置、环境？
- 做了什么假设？

---

## 阶段 3：假设与验证

**科学方法：**

### 1. 形成单一假设

- 明确陈述："我认为 X 是根因，因为 Y"
- 写下来
- 要具体，不要模糊

### 2. 最小化测试

- 做尽可能小的改动来验证假设
- 一次只变一个变量
- 不要同时修复多个东西

### 3. 验证后再继续

- 管用了？ → 进入阶段 4
- 不管用？ → 形成新的假设
- 不要往上叠加更多修复

### 4. 不懂就说

- 说"我不理解 X"
- 别装懂
- 向用户求助
- 继续调研

---

## 阶段 4：实施修复

**修复根因，而非症状：**

### 1. 创建失败测试用例

- 尽可能简单的复现
- 尽量自动化测试
- 修复之前必须先有测试
- 使用 `test-driven-development` 技能

### 2. 实施单一修复

- 针对已识别的根因
- 一次只改一处
- 不要"顺便"做改进
- 不要捆绑重构

### 3. 验证修复

```bash
# 运行指定的回归测试
pytest tests/test_module.py::test_regression -v

# 运行全量测试——确保无回归
pytest tests/ -q
```

### 4. 如果修复不管用——三次法则

- **停。**
- 数一数：你已经试过多少次修复了？
- 如果 < 3：回到阶段 1，带着新信息重新分析
- **如果 ≥ 3：停手，质疑架构（见下方第 5 步）**
- 没经过架构讨论，不要尝试第 4 次修复

### 5. 如果 3 次以上修复失败：质疑架构

**表明存在架构问题的模式：**
- 每次修复都在不同地方暴露新的共享状态/耦合
- 修复需要"大规模重构"才能实现
- 每次修复都在别处引发新问题

**停下来质疑根本问题：**
- 这个模式从根本上是对的吗？
- 我们是不是"纯粹靠惯性在坚持"？
- 应该重构架构还是继续修复症状？

**和用户讨论后再尝试更多修复。**

这可不是假设错了——这是架构本身有问题。

---

## 红灯信号——停下来，回到流程

如果你发现自己有这样想法：
- "先快速修一下，后面再查"
- "试试改 X 看看行不行"
- "一次性改好几处，跑个测试"
- "跳过测试，手动验证一下"
- "大概就是 X 的问题，修一下"
- "我不是完全理解，但这可能管用"
- "模式说要 X，但我自己调整一下"
- "主要问题有这些：[未经调查就列举修复方案]"
- 还没追踪数据流就提解决方案
- **"再试一次修复"（已经试了 2 次以上）**
- **每次修复都在别的地方冒出新问题**

**以上全部意味着：停下来。回到阶段 1。**

**如果 3 次以上修复失败：** 质疑架构（阶段 4 第 5 步）。

## 常见借口

| 借口 | 现实 |
|------|------|
| "问题很简单，不用走流程" | 简单问题同样有根因。流程对简单 bug 也很快。 |
| "紧急情况，没时间走流程" | 系统化调试比瞎猜乱撞更快。 |
| "先试这个，再调查" | 第一次修复就定调子。从一开始就做对。 |
| "确认修复有效后我再补测试" | 没测试的修复不牢靠。先写测试来证明。 |
| "一次改多处更省时间" | 无法隔离哪个起效。还会引发新 bug。 |
| "参考太长了，我自己改改这个模式" | 一知半解必然出 bug。完整读完它。 |
| "我看到问题了，修一下" | 看到症状 ≠ 理解根因。 |
| "再试一次修复"（已失败 2 次以上） | 3 次以上失败 = 架构问题。质疑模式，别继续修。 |

## 速查表

| 阶段 | 关键活动 | 成功标准 |
|------|----------|----------|
| **1. 根因** | 读报错、复现、检查变更、收集证据、追踪数据流 | 理解是什么、为什么 |
| **2. 模式** | 找正常示例、对比、找出差异 | 知道哪里不同 |
| **3. 假设** | 形成理论、最小化测试、一次一个变量 | 假设被证实或形成新假设 |
| **4. 实施** | 创建回归测试、修复根因、验证 | bug 解决，全部测试通过 |

## Agent 集成

### 调查工具

在阶段 1 中使用以下 agent 工具：

- **`search_files`** — 搜索报错字符串，追踪函数调用，定位模式
- **`read_file`** — 带行号阅读源码，精确定位分析
- **`terminal`** — 运行测试，检查 git 历史，复现 bug
- **`web_search`/`web_extract`** — 搜索报错信息，查阅库文档

### 配合 delegate_task 使用

对于复杂的多组件调试，可以派发调查子任务：

```python
delegate_task(
    goal="调查为什么 [具体测试/行为] 失败",
    context="""
    遵循系统化调试技能：
    1. 仔细阅读报错信息
    2. 复现问题
    3. 追踪数据流找到根因
    4. 汇报发现——暂时不要修复

    错误：[粘贴完整报错]
    文件：[失败代码的路径]
    测试命令：[精确命令]
    """,
    toolsets=['terminal', 'file']
)
```

### 配合 test-driven-development 使用

修复 bug 时：
1. 写一个能复现 bug 的测试（RED）
2. 系统化调试找出根因
3. 修复根因（GREEN）
4. 测试不仅证明了修复有效，还能防止回归

## 真实效果

来自实际调试数据：
- 系统化方法：15-30 分钟修完
- 胡乱修复：2-3 小时乱撞
- 一次修好率：95% vs 40%
- 引入新 bug：几乎为零 vs 常见

**不走捷径。不靠猜测。系统化永远胜出。**
